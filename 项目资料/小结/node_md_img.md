# 1. 模块整体功能

`node_md_img.py` 实现知识库文档导入流程中的 Markdown 图片处理节点 `NodeMDImg`。它解决的核心问题是：Markdown 中的本地图片既不方便后续系统访问，图片本身的视觉信息也无法直接参与文本检索，因此需要把图片转成“远程可访问地址 + 可检索的文字摘要”。

在完整导入流程中，它位于 Markdown 准备完成之后、文档切片之前：

```text
NodeEntry 判断输入类型
→ 如果输入是 PDF，由 NodePDFToMD 转成 Markdown
→ NodeMDImg 处理 Markdown 图片
→ NodeDocumentSplit 读取处理后的 Markdown 并切片
→ 后续进行主体识别、向量化和 Milvus 入库
```

节点从 `state` 读取 `md_path`，再从磁盘读取 Markdown 内容。处理成功后，它会：

- 为每张有效图片提取 Markdown 上下文；
- 调用视觉语言模型（VLM）生成不超过约 50 字的中文摘要；
- 把图片上传到 MinIO；
- 用摘要替换图片的 Alt 文本，用 MinIO URL 替换本地图片路径；
- 将结果写入同目录下的 `<原文件名>_new.md`；
- 返回新的 `md_content` 和 `md_path`，供下一个节点继续处理。

如果没有图片目录、图片目录为空，或者没有符合条件且被 Markdown 引用的图片，节点不会生成新文件，而是直接返回原始 `md_content`。

本文以 `backup/kb_main/import_process/nodes/node_md_img.py` 这个未拆分方法的学习版为主要事实来源；`kb_main` 下的同名模块是方法封装版。

# 2. 整体实现流程

学习版把完整逻辑集中在 `process()` 中，可以归纳为六个阶段：

1. 从 `state` 取得并校验 `md_path`，读取 Markdown 全文。
2. 定位 Markdown 同目录下的 `images` 文件夹，取得目录内容。
3. 筛选有效图片，确认图片被 Markdown 正确引用，并提取前后文。
4. 将图片编码为 Base64 Data URL，调用 VLM 生成中文摘要，同时用滑动时间窗口限制请求频率。
5. 将图片上传到 MinIO，并为每张图片构造远程 URL。
6. 替换 Markdown 中的图片摘要和地址，写入 `_new.md`，返回更新后的状态字段。

其中任何一个“没有图片可处理”的正常分支，都会在调用 VLM 和 MinIO 之前提前结束。

# 3. 各步骤关键实现

## 3.1 校验路径并读取 Markdown

节点首先执行：

```python
md_path = state.get("md_path")
```

如果字段不存在或值为空，记录错误并抛出异常。随后用 `Path(md_path)` 创建路径对象，并通过 `exists()` 检查路径是否存在。

校验通过后，代码以 UTF-8 编码读取整个 Markdown 文件：

```python
with open(md_path_obj, "r", encoding="utf-8") as f:
    md_content = f.read()
```

实际代码中的调用包含正确的逗号和关键字参数，上面的含义是以只读方式获取完整文本。若读取结果为空字符串，节点抛出异常。

这一阶段的输入是 `state["md_path"]`，输出是：

- `md_path_obj`：后续用于定位 `images` 目录和生成新文件路径；
- `md_content`：后续用于寻找图片引用、截取上下文和替换内容。

需要注意：节点并没有从 `state["md_content"]` 读取正文，而是始终根据 `md_path` 重新读取磁盘文件。

## 3.2 检查图片目录

图片目录固定为：

```python
images_dir_obj = md_path_obj.parent / "images"
```

也就是说，代码假定 Markdown 文件和 `images` 文件夹具有如下结构：

```text
文档目录/
├── 文档.md
└── images/
    ├── image1.png
    └── image2.jpg
```

如果 `images` 不存在，或者 `os.listdir()` 得到空列表，节点会记录警告并直接返回原始 `md_content`。这种情况属于“没有图片需要处理”，不是异常失败。

## 3.3 筛选图片并提取上下文

代码只接受以下扩展名：

```text
.jpg  .jpeg  .png  .gif  .bmp  .webp
```

扩展名判断会先转成小写，因此 `.PNG`、`.JPG` 等大写形式也可以通过。

对于每个候选文件，代码分两层确认它是否被 Markdown 使用：

1. 使用 `image_name in md_content` 做快速粗筛；
2. 使用正则表达式确认它出现在 Markdown 图片语法 `![...](...)` 中。

正则中通过 `re.escape(image_name)` 转义文件名，避免文件名中的 `.`、`+` 等字符被当作正则语法。

找到引用后，代码用 `match.span()` 得到该图片语法在全文中的开始和结束位置，再提取：

- 图片语法之前最多 250 个字符，保存为 `pre_text`；
- 图片语法之后最多 250 个字符，保存为 `post_text`。

上文开始位置使用：

```python
max(0, start_index - MAX_CONTENT_LENGTH)
```

这样图片靠近文件开头时不会产生错误的负索引，图片位于后面时也只截取最近的 250 个字符。

每张有效图片最终整理成：

```python
{
    "image_name": 图片文件名,
    "image_path": 图片本地完整路径,
    "pre_text": 图片上文,
    "post_text": 图片下文,
}
```

遍历结束后，如果列表仍为空，说明目录中虽然有内容，但没有可处理的 Markdown 图片。代码会直接返回原文，不再初始化 VLM 或连接 MinIO。

当前实现对同一个图片文件名只通过 `pattern.search()` 提取第一次出现位置的上下文；后面替换 Markdown 时，`pattern.sub()` 会替换该文件名匹配到的所有图片引用。因此，同一图片被多次引用时只生成一次摘要，摘要依据第一次引用附近的上下文。

## 3.4 调用 VLM 生成图片摘要

代码使用 LangChain 的 `init_chat_model()` 创建一个 OpenAI 兼容接口的聊天模型。模型名称、API Key、API Base、温度等参数来自 `LLMConfig`，因此具体模型由项目环境配置决定。

发送图片前，代码执行以下转换：

```text
本地图片文件
→ 读取二进制字节
→ Base64 编码
→ 根据扩展名推断 MIME 类型
→ 拼成 data:<mime_type>;base64,<数据>
```

VLM 消息同时包含两类内容：

- `image_url`：实际不是公网 URL，而是内嵌图片数据的 Base64 Data URL；
- `text`：图片前后文，以及“用中文在 50 字以内生成摘要”的要求。

模型响应的 `res.content` 被保存为图片的 `summary`。这样，摘要既能写入 Markdown 的 Alt 文本，也能随着后续文档切片进入文本处理链路。

学习版没有单独捕获某一张图片的 VLM 调用异常。如果 `vlm.invoke()` 失败，异常会向上传递到 `NodeBase.__call__()`，由节点基类记录“节点执行失败”后继续抛出，整个节点随之中断。

## 3.5 使用滑动时间窗口限流

代码使用 `deque(maxlen=30)` 保存最近请求的时间戳，并通过 `time.monotonic()` 获取单调递增时间。

每次准备调用模型前会执行：

1. 删除距离当前时间超过 60 秒的旧时间戳；
2. 如果队列已有 30 个请求，计算最早请求离开 60 秒窗口还需要多久；
3. 使用 `time.sleep()` 阻塞等待；
4. 醒来后重新获取时间并再次清理过期记录；
5. 将本次请求时间加入队列。

它表达的规则是：单次 `process()` 执行期间，任意约 60 秒窗口内最多发出 30 次 VLM 请求。

代码注释中的“令牌桶算法”与实际行为不一致。这里没有令牌生成、令牌消费或桶容量补充过程，准确说法是“基于时间戳队列的滑动窗口限流”。此外，队列是 `process()` 内的局部变量，每次执行节点都会重新创建，因此它不负责不同任务之间的统一限流。

## 3.6 上传图片并构造 MinIO URL

摘要生成完成后，代码通过 `get_minio_client()` 获得 MinIO 客户端，并从 `MinIoConfig` 读取：

- Bucket 名称；
- 图片上传目录；
- MinIO Endpoint。

随后使用 `fput_object()` 逐张上传图片：

```python
object_name = f"{upload_dir}/{image_name}"
```

上传后，代码自行按照下面的形式拼接访问地址：

```text
http://<endpoint>/<bucket>/<upload_dir>/<image_name>
```

每张图片的数据由原来的 `image_name`、`image_path`、`summary`，进一步增加为包含 `url` 的字典。

`fput_object()` 的返回值目前保存到了 `result`，但后续没有读取它；真正写入 Markdown 的 URL 来自代码自行拼接的字符串。

## 3.7 替换 Markdown 并写入新文件

代码再次用图片文件名构建正则表达式，然后通过 `pattern.sub()` 把原图片语法替换为：

```markdown
![VLM 生成的图片摘要](MinIO 图片 URL)
```

完成全部替换后，新文件路径为：

```python
new_md_path_obj = md_path_obj.parent / f"{md_path_obj.stem}_new.md"
```

原 Markdown 文件不会被覆盖。节点把新内容写入 `_new.md`，最终返回：

```python
{
    "md_content": md_content,
    "md_path": new_md_path_obj,
}
```

这里的 `md_path` 实际是 `Path` 对象，而 `ImportGraphState` 中将其标注为 `str`。当前下游 `NodeDocumentSplit` 会再次把它传给 `Path()`，所以实际调用可以兼容，但类型标注与运行时值并不完全一致。

# 4. 为什么这样设计

## 4.1 为什么在切片前处理图片

文档切片之后，图片与原始上下文可能被分散到不同片段中。先处理图片，可以在文档结构仍然完整时取得图片附近的文字，并把图片摘要写回原位置。后续切片获得的就不再只是一个本地图片路径，而是带有视觉语义的 Markdown 内容。

## 4.2 为什么同时向 VLM 提供图片和上下文

只看图片时，模型可能无法判断图片在当前文档中的具体用途。例如同一张结构图可能表示系统架构、业务流程或设备组成。附近文字可以帮助模型缩小语义范围，使摘要更贴近文档主题。

当前代码无法证明“前后各 250 字”是唯一正确长度；可以确认的是，它在补充上下文和控制提示词体积之间做了一个固定取舍。

## 4.3 为什么把摘要写入 Alt 文本

Markdown 图片的 Alt 文本本身就是图片的文字说明位置。将 VLM 摘要写进去后，后续文本切片、向量化和检索流程可以接触到原本只存在于视觉内容中的信息，同时仍保持合法的 Markdown 图片结构。

## 4.4 为什么上传到 MinIO

本地相对路径只对生成 Markdown 的机器和目录结构有效。上传到对象存储后，Markdown 可以通过 HTTP 地址引用图片，使后续服务不必依赖原始本地目录。

## 4.5 为什么先粗筛再使用正则

字符串包含判断比完整正则匹配更简单。先排除正文里根本没有出现文件名的图片，可以减少不必要的正则搜索；正则再负责确认它确实属于 Markdown 图片语法，而不只是正文中偶然出现了同名字符串。

## 4.6 为什么生成 `_new.md`

写入新文件可以保留原始 Markdown，便于对照处理前后的内容，也避免图片处理过程中直接覆盖原始结果。下一个节点通过更新后的 `md_path` 读取新文件。

# 5. 数据流转

正常处理路径如下：

```text
输入 ImportGraphState
→ 读取 state["md_path"]
→ 从磁盘读取 Markdown，得到 md_content
→ 定位同目录 images 文件夹
→ os.listdir() 得到文件名列表
→ 扩展名筛选 + Markdown 图片引用正则确认
→ 每张图片形成 image_name/image_path/pre_text/post_text
→ 图片二进制转 Base64 Data URL
→ VLM 根据图片和上下文返回 summary
→ 图片上传 MinIO并增加 url
→ 替换 Markdown 的 Alt 文本和图片路径
→ 写入 <原文件名>_new.md
→ 返回新的 md_content 和 md_path
→ LangGraph 将返回字段合并进 State
→ NodeDocumentSplit 根据新 md_path 读取并切分文档
```

提前返回路径如下：

```text
md_path 有效且 Markdown 非空
→ images 目录不存在 / 目录为空 / 没有有效图片引用
→ 不调用 VLM，不上传图片，不生成 _new.md
→ 仅返回原始 md_content
→ State 中原有 md_path 继续保留
```

# 6. 异常处理与注意事项

## 6.1 当前已经处理的情况

- `state` 未提供有效 `md_path`：记录错误并抛出异常。
- `md_path` 不存在：记录错误并抛出异常。
- Markdown 文件内容为空：记录错误并抛出异常。
- `images` 目录不存在：记录警告，返回原文。
- `images` 目录为空：记录警告，返回原文。
- 文件扩展名不受支持：跳过该文件并记录警告。
- 图片文件名没有出现在正文中：跳过并记录警告。
- 文件名出现了，但没有匹配到 Markdown 图片语法：跳过并记录警告。
- 图片目录有内容但没有任何有效图片：记录警告，返回原文。
- 节点内部其他异常：`NodeBase.__call__()` 会统一记录失败日志并重新抛出。

## 6.2 当前需要注意的边界

- `exists()` 只能说明路径存在，没有明确确认 `md_path` 是普通文件；如果传入目录，读取时仍会失败。
- 图片必须位于 Markdown 同目录下固定名称的 `images` 文件夹，其他目录结构不会被扫描。
- 正则主要面向当前项目生成的常规 `![alt](path)` 语法，不是完整的 Markdown 解析器。
- 同一图片被多次引用时，只使用第一次引用的上下文生成摘要，但会替换全部匹配引用。
- 学习版的单张图片 VLM 请求失败会中断整个节点；它不会跳过失败图片继续处理。
- 图片读取、模型初始化与调用、MinIO 连接和上传、输出文件写入都可能抛出外部异常，目前由节点基类统一记录后向上抛出。
- `data_url` 变量被构造后没有直接使用，消息中又重新拼接了一次相同格式的数据。
- 限流队列只在本次节点执行期间有效，不代表整个进程、多个任务或多个实例共享同一限流额度。
- `time.sleep()` 是同步阻塞等待；图片数量较多且触发上限时，节点会停在当前位置直到窗口释放。

## 6.3 注释与实际行为不一致

- 注释把限流称为“令牌桶算法”，实际是基于时间戳队列的滑动窗口。
- 某些流程说明写成“从 state 读取 Markdown 路径和内容”，实际只从 State 读取路径，正文来自磁盘文件。
- `_new.md` 可以视作处理后的新版本，但代码没有专门的备份操作，也没有复制原文件；只是因为不覆盖原文件，所以原文件自然得到保留。

# 7. 核心知识点

- **LangGraph State**：节点从共享状态读取 `md_path`，返回 `md_content` 和新的 `md_path`，由图框架合并后传给下游节点。
- **模板方法式节点封装**：`NodeMDImg` 实现 `NodeBase.process()`，实际调用经过 `NodeBase.__call__()`，从而统一记录节点开始、完成和失败日志。
- **`pathlib.Path`**：用于检查路径、取得父目录和文件主名，以及组合 `images`、`_new.md` 等路径。
- **文件 IO**：以 UTF-8 读取 Markdown，以二进制读取图片，再将处理后的文本写入新 Markdown 文件。
- **正则表达式**：确认图片是否出现在 Markdown 图片语法中，并在最后替换整段图片标记；`re.escape()` 用于安全处理文件名。
- **字符串切片**：根据正则匹配位置提取图片前后各最多 250 个字符，作为 VLM 的语义上下文。
- **Base64 Data URL**：把本地图片转成能够直接放入多模态消息的数据形式，不需要先把图片上传到公网再调用模型。
- **MIME 类型**：使用 `mimetypes.guess_type()` 根据图片路径推断 `image/png`、`image/jpeg` 等类型，帮助模型接口识别图片数据格式。
- **LangChain 聊天模型**：通过 `init_chat_model()` 初始化 OpenAI 兼容的多模态模型，通过 `invoke()` 同步获得图片摘要。
- **`deque` 与滑动窗口**：保存最近 60 秒的请求时间戳，在数量达到上限时阻塞等待，用于控制单次任务的调用速率。
- **`time.monotonic()`**：只关心时间间隔，不受系统时钟被手动调整的影响，适合计算限流窗口。
- **MinIO 对象存储**：使用 `fput_object()` 上传本地图片，并把 Markdown 的本地引用改为远程 HTTP 地址。
- **Markdown Alt 文本**：将图片视觉摘要写入 `![摘要](URL)` 的方括号部分，使后续纯文本处理也能获得图片语义。

# 8. 面试复述版

我在这个模块中实现的是知识库导入流程里的 Markdown 图片处理节点。它位于 Markdown 准备完成之后、文档切片之前，主要解决两个问题：一是本地图片路径不方便后续服务访问，二是图片里的信息不能直接参与文本检索。

节点首先从 LangGraph 的 State 中读取 `md_path`，检查路径和文件内容是否有效，然后定位 Markdown 同目录下的 `images` 文件夹。对于目录里的文件，我先按扩展名过滤，再通过字符串包含判断和正则表达式两层检查，确认图片确实被 Markdown 的图片语法引用。匹配成功后，我根据图片引用的位置提取前后各最多 250 个字符，作为图片的文档上下文。

接下来，我把图片读取成二进制并编码成 Base64 Data URL，再把图片和上下文一起交给视觉语言模型，让模型生成简短的中文摘要。调用模型时，我使用一个保存请求时间戳的双向队列做滑动窗口限流：只保留最近 60 秒的请求，达到 30 次后就等待最早的请求离开窗口。这里本质上是滑动窗口，不是令牌桶。

得到摘要后，我把图片上传到 MinIO，构造远程访问 URL，再把原 Markdown 图片语法替换成“摘要作为 Alt 文本、MinIO 地址作为图片链接”的形式。处理后的内容不会覆盖原文件，而是写入同目录下的 `_new.md`，最后把新内容和新路径返回给 State，下游文档切片节点就会读取处理后的文件。

这个模块已经处理了路径缺失、空文件、图片目录不存在、无有效图片等情况。需要注意的是，学习版对模型调用、MinIO 上传等外部失败没有做局部恢复，发生异常时会由节点基类记录日志并让整个节点失败。另外，同一图片多次引用时只根据第一次出现的上下文生成一次摘要。整体上，这个节点完成了本地图片持久化和图片视觉语义文本化，为后续切片、向量化和检索提供了统一的文本入口。

# 9. 面试可能追问的问题

1. 为什么图片处理必须安排在文档切片之前？

# 10. 可优化点

## 10.1 【当前已经实现】

- 已校验 `md_path` 是否提供、路径是否存在以及 Markdown 内容是否为空。
- 已对图片扩展名和 Markdown 引用关系进行两层过滤。
- 已正确使用 `max(0, ...)` 处理图片靠近文件开头时的切片边界。
- 已统一使用 `pre_text`、`post_text` 保存和读取图片上下文。
- 已在没有有效图片时提前返回，避免无意义地调用外部服务。
- 已使用 `time.monotonic()` 和 60 秒时间戳队列实现单次任务内的滑动窗口限流。
- 已将 VLM 摘要写入 Alt 文本，并使用实际构造的 MinIO URL 替换本地路径。
- 已通过生成 `_new.md` 保留原始 Markdown 文件。

## 10.2 【学习版与封装版的实际差异】

- `backup` 学习版把全部主流程写在一个 `process()` 中；`kb_main` 版按校验、上下文提取、摘要生成、上传和替换拆成多个方法。拆分方式改变了代码组织，没有改变核心业务目标。
- `kb_main` 版为 MIME 类型提供了 `image/jpeg` 默认值；学习版直接使用 `guess_type()` 的结果。
- `kb_main` 版捕获单张图片的 VLM 调用异常，并用“图片摘要生成失败”作为占位摘要继续执行；学习版会让异常向上传递并中断节点。这是两版目前最明显的运行行为差异。

## 10.3 【未来可以优化】

- 使用 `md_path_obj.is_file()` 明确拒绝目录路径，并针对文件编码错误提供更清楚的提示。
- 用 Markdown 解析器代替简化正则，以更完整地支持带标题、转义字符或其他复杂形式的图片语法。
- 对同一图片的多次引用分别收集上下文，或者合并多个位置的上下文后再生成摘要。
- 把窗口大小、请求上限和摘要字数从硬编码常量移到配置中，并依据实际模型服务的限流规则设置。
- 如果需要跨任务统一限流，应把限流器提升到共享层，而不是在每次 `process()` 中重新创建队列。
- 对 VLM、MinIO 和文件写入失败设计清晰策略，例如有限次数重试、跳过单张失败图片或终止整份文档，并明确哪些失败允许继续。
- 对模型返回的摘要做基础清洗，避免特殊字符破坏 Markdown 的 Alt 文本语法。
- 统一 `ImportGraphState.md_path` 的类型：要么返回字符串，要么把 State 标注改为允许 `Path`，减少类型理解偏差。
- 删除未使用的导入、说明字符串、`data_url` 和上传返回值变量，使学习代码更聚焦于真实执行路径。
