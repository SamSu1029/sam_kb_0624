# 项目学习复盘小结生成模板
目前处于学习阶段，核对时只看逻辑bug，不管工程bug，但是工程bug可以在小结正文中的可优化点里说明
如果代码有bug，先指出问题，不生成小结，直到用户确认可以生成
不主动执行代码修改，除非用户要求

## 一、文档保存与命名规则

1. 所有学习复盘小结使用 Markdown（`.md`）格式。
2. 所有小结统一保存到：`项目资料/小结/`。
3. 每个模块的小结文件名必须与对应 Python 模块文件名完全一致，只修改扩展名。

   例如：

   - `node_pdf_to_md.py` 对应 `项目资料/小结/node_pdf_to_md.md`
   - `node_document_split.py` 对应 `项目资料/小结/node_document_split.md`

   不要自行缩写、翻译或者修改模块名称。
4. 本模板固定保存为：`项目资料/小结/小结生成模板.md`。
5. 以后生成新的模块小结时，优先读取并遵守本模板。

## 二、非常重要：代码注释的使用原则

用户目前处于学习阶段，代码中的一部分注释是用户根据当前理解编写的。因此，生成小结时必须遵守以下原则：

1. 不要默认认为代码注释一定正确。
2. 注释只能作为辅助参考信息，不能直接作为小结中的事实依据。
3. 分析模块时，应优先依据：

   - 实际代码行为
   - 函数调用关系
   - 数据流转
   - 条件判断
   - 返回值
   - State 的读取与写入
   - 实际调用的 API、类和函数
   - 当前项目中能够确认的上下文

4. 如果注释和实际代码行为存在冲突：

   - 必须以实际代码为准。
   - 不要照抄错误注释。
   - 在小结中指出存在“注释与代码行为不一致”的情况。
   - 简单解释实际代码真正做了什么。

5. 如果某条注释无法通过实际代码验证，不要直接把它写成事实。
6. 不要因为代码中已经存在中文注释，就直接复制这些注释作为小结内容。需要自行阅读和理解实际代码，然后重新组织总结。

核心原则：**代码行为是主要事实来源，注释只是参考资料。**

## 三、这份小结的用途

学习复盘小结主要用于：

- 项目完成后的知识沉淀
- 以后快速恢复对项目的记忆
- 面试前复习项目
- 练习向面试官口述项目
- 检查自己是否真正理解代码
- 理解“为什么这样设计”，而不仅仅是记住代码

小结不要写成逐行代码解释，不要写成 API 文档，也不要单纯翻译代码和注释。

重点是：**这个模块干什么 → 怎么做 → 为什么这样做 → 数据怎么流转 → 有什么关键点 → 面试怎么讲。**

## 四、小结正文结构

# 1. 模块整体功能

从整体角度说明：

- 当前模块或节点主要解决什么问题？
- 它在整个项目流程中处于什么位置？
- 上一步通常是什么？
- 下一步通常是什么？
- 它接收什么数据？
- 最终输出、返回或修改了什么数据？

这一部分要比较通俗。以后即使已经忘记代码细节，只阅读这一部分，也应该能够马上回忆起这个模块是干什么的。

# 2. 整体实现流程

把当前模块的完整执行过程拆成若干“大步骤”。

例如：

1. 读取并校验输入。
2. 申请资源。
3. 处理数据。
4. 获取处理结果。
5. 更新 State。

具体步骤必须根据当前实际代码确定，不要套用示例。这里只描述主干流程，以便以后快速恢复整个模块的执行逻辑。

# 3. 各步骤关键实现

按照上一部分的大步骤逐个展开。每一个大步骤说明：

- 这一步具体做什么
- 为什么需要这一步
- 使用了哪些关键变量、函数、类、API 或第三方库
- 输入是什么
- 数据发生了什么变化
- 输出是什么
- 有哪些重要判断条件
- 后续代码如何使用这一步产生的结果

不要逐行解释代码，只保留真正影响理解的关键逻辑。

# 4. 为什么这样设计

提炼当前代码中比较重要的设计思路，例如：

- 为什么需要这个步骤？
- 为什么采用当前这种实现？
- 为什么需要这个判断？
- 为什么某些数据需要写入 State？
- 为什么调用这个外部 API？
- 为什么这里要拆成两个请求？
- 如果省略某一步可能出现什么问题？

重点回答“为什么”。如果某个设计原因无法从当前代码或可靠项目上下文中确定，必须明确标注：

> 当前代码无法确定设计者的真实意图，以下属于合理推测。

不要把推测写成事实。

# 5. 数据流转

单独把当前模块的数据流梳理清楚，尽可能用简单的流程表示，例如：

```text
输入 State
↓
读取 file_path
↓
调用外部 API
↓
获得处理结果
↓
写回 State
```

具体内容必须以当前代码为准。目标是能够快速回答：“数据从哪里来，经过了什么处理，最后去了哪里？”

# 6. 异常处理与注意事项

单独整理：

- 当前代码已经处理了哪些异常
- 每种异常分别发生在哪个阶段
- 哪些地方容易出错
- 有哪些边界情况
- 有哪些外部依赖或环境因素
- 有哪些容易混淆的概念
- 哪些细节以后复习时必须注意

如果代码没有处理某种异常，不要写成“已经处理”，可以放到后面的“可优化点”中。

# 7. 核心知识点

提炼当前模块实际涉及的重要知识点，例如 Python、HTTP、`requests`、LangGraph State、LangChain、文件 IO、`pathlib`、JSON、异常处理、MinerU API、Milvus、Embedding 等。

只列当前模块真正涉及的知识。每个知识点简单说明：“这个知识点在当前模块里具体用来干什么。”不要泛泛介绍理论。

# 8. 面试复述版

基于当前实际代码，生成一份适合面试时口头讲述的版本。

要求：

- 使用第一人称。
- 以“我在这个模块中……”的角度表达。
- 不逐行讲代码。
- 不背 API。
- 语言自然。
- 技术描述准确。
- 按照“模块作用 → 在整个项目中的位置 → 整体流程 → 关键实现 → 为什么这么设计 → 异常和注意事项 → 最终结果”组织。
- 控制在大约 2～3 分钟能够讲完。

目标是以后面试前可以直接使用这一部分练习项目口述。

# 9. 面试可能追问的问题

根据当前模块实际代码，整理 5～10 个面试官可能继续追问的问题，重点围绕：

- 为什么这样设计？
- 数据怎么流转？
- 为什么使用这个技术？
- 某一步失败怎么办？
- 为什么不用另一种实现？
- 当前方案有什么不足？
- 如果数据量增加怎么办？
- 如果重新设计会怎么优化？

这里只给问题，不直接提供答案。这些问题用于用户自行回答，检查是否真正理解了模块。

# 10. 可优化点

如果当前代码存在值得改进的地方，可以单独整理。

必须明确区分：

- 【当前已经实现】
- 【未来可以优化】

绝对不要把“未来可以优化的方案”描述成当前项目已经具备的能力。这一部分只总结和提出建议，不直接修改 Python 代码。

## 五、分析原则

生成小结时必须遵守：

1. 以当前项目实际代码为主要依据。
2. 不要脑补不存在的功能。
3. 用户的代码注释只能参考，不能直接当成事实。
4. 如果注释与代码冲突，以代码为准。
5. 如果无法确定某件事情，明确写：“当前代码无法确定”。
6. 区分当前实际实现、设计意图推测和未来优化方案。
7. 不要逐行翻译代码。
8. 重点关注模块职责、主干流程、数据流、关键技术、设计原因、异常处理和面试表达。
9. 内容面向一个正在学习阶段的开发者。
10. 总结的目标不是“看起来专业”，而是让用户以后能够真正看懂、想起来、讲出来。

## 六、同名学习版与封装版的对比规则

当前项目中，`backup` 保存未进行方法封装的学习版，`kb_main` 保存方法封装后的版本。两者目标功能相同。

生成模块小结时：

1. 以用户当前明确指定的文件版本作为小结的主要事实来源。
2. 方法是否拆分、日志文字、轮询等待 2 秒或 3 秒等不影响核心功能的差异，不作为功能问题报告。
3. 如果 `backup` 和 `kb_main` 的同名模块存在明显的实现逻辑或功能差异，并且该差异可能导致功能错误、流程中断、错误结果、数据损坏或长时间卡死，必须提醒用户。
4. 只指出存在显著影响的差异，不擅自修改任一版本代码。
5. 必须明确说明问题出现在哪个版本中，以及另一个版本是否已经处理。

## 七、文件修改边界

生成小结的任务只允许：

1. 新增或更新 `项目资料/小结/小结生成模板.md`。
2. 新增或更新当前指定模块对应的小结 Markdown 文件。

除上述 Markdown 文件外：

- 不要修改 Python 源代码。
- 不要修改配置文件。
- 不要修改 `.env`。
- 不要修改 `pyproject.toml`。
- 不要修改 `uv.lock`。
- 不要修改 `AGENTS.md`。
- 不要安装依赖。
- 不要执行与生成小结无关的项目修改。

如果在分析代码时发现问题，只记录在小结的“可优化点”中，不直接修改代码。
