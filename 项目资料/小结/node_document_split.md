# 1. 模块整体功能

`node_document_split.py` 实现知识库导入流程中的文档切片节点 `NodeDocumentSplit`。它负责读取已经准备好的 Markdown 文件，先按照 Markdown 标题整理章节，再将过长章节拆成带重叠的较小文本块，最终把切片列表写回 LangGraph State。

它在完整流程中的位置是：

```text
NodeEntry 判断输入文件类型
→ PDF 文件由 NodePDFToMD 转成 Markdown
→ NodeMDImg 处理 Markdown 中的图片
→ NodeDocumentSplit 按章节和长度切片
→ NodeItemNameRecognition 进行主体识别
→ NodeBGEEmbedding 生成向量
→ NodeImportMilvus 写入向量数据库
```

节点主要从 `state` 接收：

- `md_path`：需要切片的 Markdown 文件路径；
- `file_title`：整份文件的标题。没有提供时，使用 Markdown 文件名去掉扩展名后的结果。

节点不使用 `state["md_content"]`，而是根据 `md_path` 重新读取磁盘文件。处理完成后返回：

```python
{"chunks": final_chunks_list}
```

每个切片包含 `title`、`content`、`file_title` 和 `part`。此外，节点会在原 Markdown 文件同目录生成 `<原文件名>_backup.md`，其中实际保存的是格式化后的 JSON 切片数据。

本文以 `kb_main/import_process/nodes/node_document_split.py` 这个方法封装版为主要事实来源，并与 `backup` 下的学习版进行对照。

# 2. 整体实现流程

封装版通过 `process()` 串联三个阶段：

1. `process_md_content()`：检查路径、确定文件标题、读取 Markdown，并统一换行符。
2. `get_section_list()`：识别代码围栏和一级到六级 Markdown 标题，把全文整理成章节列表。
3. `get_chunks_list()`：保留短章节和含 HTML 表格的章节，对其他长章节进行递归字符切分，增加切片编号并生成备份文件。
4. `process()` 将最终列表包装为 `{"chunks": ...}` 返回，供 LangGraph 合并到 State。

这里采用的是“两级切分”：先尊重文档的章节结构，再根据长度切分过长章节。它不是简单地从全文每隔固定字符截断。

# 3. 各步骤关键实现

## 3.1 校验输入并读取 Markdown

`process_md_content()` 首先读取：

```python
md_path = state.get("md_path", "")
```

如果 `md_path` 没有提供，或者对应路径不存在，代码记录错误并抛出异常。路径有效后，通过 `Path(md_path)` 得到 `md_path_obj`。

`file_title` 来自 `state["file_title"]`。如果没有传入，则使用：

```python
file_title = md_path_obj.stem
```

随后以 UTF-8 编码读取整个文件。只有读取结果恰好是空字符串时才会被判定为空文件；只包含空格或换行的文件目前仍会继续处理。

最后统一三种常见换行形式：

```text
\r\n → \n
\r   → \n
\n   → 保持不变
```

该方法返回 `file_title`、`md_content` 和 `md_path_obj`，分别供后续章节元数据、正文分析及备份路径生成使用。

## 3.2 按 Markdown 标题整理章节

`get_section_list()` 先通过 `md_content.split("\n")` 得到原始行列表，然后使用两个正则：

```python
code_pattern = r"^(`{3,}|~{3,})"
title_pattern = r"^\s*#{1,6}\s+.+"
```

它们分别用于识别：

- 三个及以上反引号或波浪号开头的代码围栏；
- 使用一到六个 `#`、并且 `#` 后至少有一个空白字符的标题行。

循环判断时会对局部变量 `line` 执行 `strip()`。在当前 `kb_main` 版中，这不会直接修改 `line_split_list` 保存的原文，只用于正则判断。

`in_code_block` 表示当前是否位于围栏代码块内，`marker` 保存开始围栏。只有不在代码块内时，匹配到的标题才会作为新的章节边界。因此，代码块内形如 `# 示例` 的内容不会被误当成普通章节标题。

每遇到一个新标题，代码就通过 `current_index:idx` 取得上一个章节的全部原始行，并封装为：

```python
{
    "title": 章节标题或"无标题",
    "content": 章节原始文本,
    "file_title": 整份文件标题,
}
```

如果第一个标题之前存在前言内容，这部分会单独成为标题为“无标题”的章节。循环结束后，还会把最后一个标题到文件末尾的内容补入列表，避免最后一章丢失。

## 3.3 判断章节是否需要继续切分

`get_chunks_list()` 将最大正文长度固定为 300，并创建：

```python
RecursiveCharacterTextSplitter(
    chunk_size=300,
    chunk_overlap=30,
    separators=["\n\n", "\n", "。", "！", "？", "；", "!", "?", ";", " "]
)
```

切分器会优先尝试语义相对完整的边界：先找段落和换行，再找中英文标点，最后找空格。相邻切片保留约 30 个字符的重叠，用来降低信息刚好落在边界处而失去上下文的问题。

判断长度前，普通有标题章节会去掉首行标题，只用正文 `real_content` 参与长度判断和二次切分。这样可以避免把标题长度计入正文阈值；真正生成长章节切片时，标题会重新放到每个切片开头。

## 3.4 处理短章节和表格章节

满足任一条件时，章节不会交给文本切分器：

```python
len(real_content) < 300 or '<table' in real_content
```

此时直接保留原章节字典，并增加：

```python
"part": 0
```

因此 `part == 0` 表示该章节作为一个整体保留，并不是“长章节的第零个切片”。

代码只要在正文中发现小写字符串 `<table`，无论整个章节多长，都会保留整章。这体现了避免把 HTML 表格拆散的意图，但也意味着表格章节不受 300 字长度限制。

## 3.5 切分长章节

不包含 `<table` 且正文长度大于等于 300 时，代码调用：

```python
chunks = splitter.split_text(real_content)
```

然后从 1 开始为各片段编号：

```python
for idx, chunk in enumerate(chunks, start=1):
```

每个长章节切片被整理成：

```python
{
    "title": title,
    "content": title + "\n\n" + chunk,
    "file_title": file_title,
    "part": idx,
}
```

每一片都重复加入章节标题，目的是让片段脱离原文后仍然保留所属章节语义。`part` 则表示它在当前章节中的顺序；每进入一个新章节，编号会重新从 1 开始。

对于过长的“无标题”章节，当前实现同样会在每个切片开头加入字面量“无标题”。这是实际代码行为，不代表原文中真的存在这个标题。

## 3.6 生成本地切片备份

全部章节处理完后，代码根据输入路径生成：

```python
backup_path = md_path_obj.parent / f"{md_path_obj.stem}_backup.md"
```

`json_format()` 使用 `ensure_ascii=False` 和四空格缩进把切片列表转换成易读 JSON，然后以 UTF-8 写入该文件。

需要注意，文件扩展名虽然是 `.md`，内容却是 JSON 数组，而不是 Markdown 正文。相同输入文件再次执行时会覆盖同名备份文件。

# 4. 为什么这样设计

## 4.1 为什么先按标题分章，再按长度切片

如果直接从全文按固定长度切割，一个切片可能横跨两个主题不同的章节。先识别标题边界，可以尽量让每个片段只属于一个章节；只有章节本身过长时才继续拆分，能更好地保留文档结构。

## 4.2 为什么每个长切片都重复标题

后续向量化和检索通常以单个切片为单位。切片离开原文后，如果只有局部正文，可能无法判断它属于哪个主题。重复加入章节标题，可以为每个切片补充稳定的主题上下文。

## 4.3 为什么需要重叠内容

完全无重叠的切片会把边界两侧的句子或概念隔开。设置 30 个字符的重叠，使后一个切片保留一部分前文，从而降低边界切割造成的语义损失。

当前代码无法证明 300 和 30 是所有文档的最优值；可以确认的是，它们分别控制目标切片长度和相邻上下文重叠量。

## 4.4 为什么代码块内的 `#` 不能作为标题

Markdown 代码块经常包含注释、Shell 命令或示例文本，例如 `# comment`。如果不记录 `in_code_block`，这些内容可能被误识别成文档标题，导致章节被错误拆开。

## 4.5 为什么表格章节不继续切分

HTML 表格依赖完整的标签结构和行列关系。普通字符切分可能把开始标签、表格行和结束标签拆到不同片段中，使表格结构残缺。当前实现选择只要发现 `<table` 就保留整个章节。

## 4.6 为什么返回局部 State，而不是完整 State

节点只返回自己新产生的 `chunks` 字段。LangGraph 会把节点返回结果合并到共享 State，因此该节点不需要复制所有已有字段。这使节点职责集中在文档切片。

# 5. 数据流转

```text
输入 ImportGraphState
→ 读取 state["md_path"] 和 state["file_title"]
→ file_title 缺失时使用 Markdown 文件名
→ 从 md_path 以 UTF-8 读取 md_content
→ 统一换行符
→ 按行扫描 Markdown
→ 通过代码围栏状态排除代码块内的伪标题
→ 根据 H1～H6 标题边界生成 section_list
→ 每个 section 得到 title/content/file_title
→ 去掉标题首行，取得 real_content
→ 短正文或含 <table：整体保留，part=0
→ 其他长正文：按 300/30 规则切分，part 从 1 递增
→ 每个长切片重新补上章节标题
→ final_chunks_list 转成格式化 JSON
→ 写入 <原文件名>_backup.md
→ 返回 {"chunks": final_chunks_list}
→ LangGraph 将 chunks 合并进 State
→ 传给 NodeItemNameRecognition
```

# 6. 异常处理与注意事项

## 6.1 当前已经处理的情况

- `md_path` 未提供：记录错误并抛出异常。
- `md_path` 对应路径不存在：记录错误并抛出异常。
- Markdown 文件读取结果为空字符串：记录错误并抛出异常。
- `file_title` 未提供：自动使用文件名主干，不中断流程。
- Windows、旧式 Mac 和 Unix 换行符不一致：统一转换为 `\n`。
- 代码块中出现标题形式的文本：在围栏状态正常闭合时不会作为章节标题。
- 节点内部其他异常：`NodeBase.__call__()` 会统一记录“节点执行失败”并重新抛出。

## 6.2 当前需要注意的边界

- 只包含空格或换行的文件不等于空字符串，因此不会触发“文件内容为空”。
- 路径只检查 `exists()`，没有明确检查是否为普通文件；目录路径会在 `open()` 时失败。
- 标题只支持 `#` 到 `######` 形式，不处理 Setext 风格的 `===` 或 `---` 标题。
- 当前围栏结束判断要求结束标记与开始标记完全相同。Markdown 中使用更多同类符号关闭围栏时，代码可能无法退出代码块状态，随后出现的标题也不会被识别。
- 围栏正则只检查行首符号，没有严格区分“带语言名称的开始围栏”和“只能跟空白的结束围栏”。
- `<table` 判断区分大小写，`<TABLE>` 不会进入表格保护分支。
- 只要章节包含 `<table` 就整章不切分，超长表格章节可能明显超过 300 字。
- 输出备份使用 `.md` 扩展名，但内容是 JSON，复习时不要把它误认为 Markdown 文档。
- 文件写入、UTF-8 解码和切分器执行产生的异常没有在本节点局部恢复，而是交给 `NodeBase` 记录后继续抛出。

## 6.3 当前 `kb_main` 的标题前导空格问题

当前 `kb_main` 版在扫描时执行 `line = line.strip()`，所以标题正则可以识别前面带空格的标题；但生成章节时又对原始文本使用：

```python
section_content.startswith("#")
```

原始标题如果是 `   # 标题`，这个判断会得到 `False`，最终标题被记录成“无标题”，后续也无法正确剥离标题首行。

`backup` 学习版已经修正了这部分逻辑：它保留原始正文，只单独规范化标题行，并根据生成的标题字段决定是否剥离首行。按照用户当前安排，`kb_main` 暂未同步修改，因此这是两版目前存在的实际逻辑差异。

# 7. 核心知识点

- **LangGraph State**：节点从共享状态读取 `md_path` 和 `file_title`，只返回新增的 `chunks` 字段。
- **模板方法式节点封装**：`NodeDocumentSplit` 实现 `NodeBase.process()`；节点实际执行经过 `NodeBase.__call__()`，从而统一记录开始、完成和失败日志。
- **`pathlib.Path`**：用于检查路径、取得文件名主干、父目录，并构造切片备份路径。
- **文件 IO**：以 UTF-8 读取 Markdown，再把格式化后的切片 JSON 写入本地文件。
- **正则表达式**：用于识别 Markdown 围栏代码块以及一到六级 ATX 标题。
- **状态机思想**：通过 `in_code_block` 和 `marker` 记录当前解析状态，避免把代码块内的 `#` 当作文档标题。
- **列表切片与索引**：使用 `current_index:idx` 收集两个标题之间的全部行，并在循环结束后补充最后一章。
- **`RecursiveCharacterTextSplitter`**：按照有优先级的分隔符递归寻找切点，把过长章节拆成较小文本块。
- **切片重叠**：相邻片段保留 30 个字符左右的重复上下文，减少语义在边界处断裂。
- **元数据补充**：`title` 表示章节标题，`file_title` 表示整份文件标题，`part` 表示章节是否切分及片段顺序。
- **JSON 序列化**：`json_format()` 使用中文不转义和缩进格式，将切片列表保存为便于人工检查的文本。

# 8. 面试复述版

我在这个模块中实现的是知识库文档导入流程里的 Markdown 切片节点。它位于图片处理之后、主体识别和向量化之前，主要目标是把一整份 Markdown 文档转换成适合后续检索和向量化的文本片段，同时尽量保留章节结构和上下文。

节点首先从 LangGraph State 中读取 `md_path` 和 `file_title`。如果没有文件标题，我就用文件名去掉扩展名作为默认值。随后以 UTF-8 从磁盘读取 Markdown，并把不同平台的换行符统一成 `\n`。

切片采用两级策略。第一层先按 Markdown 标题分章。我逐行扫描文档，通过正则识别一到六级标题，同时用 `in_code_block` 和围栏标记记录当前是否处于代码块中，避免把代码示例里的 `#` 误判为标题。每一章会保存章节标题、完整内容和文件标题。

第二层根据章节正文长度继续切分。正文小于 300 字时整章保留，`part` 记为 0；如果章节包含 HTML 表格，也整章保留，避免普通字符切分破坏表格结构。其他长章节使用 `RecursiveCharacterTextSplitter`，优先在段落、换行和标点处寻找切点，目标长度是 300，相邻片段重叠 30 个字符。每个长切片都会重新加上章节标题，并从 1 开始记录 `part`，这样单个片段脱离原文后仍能知道主题和顺序。

最终，我把切片列表以格式化 JSON 写入原文档同目录下的 `_backup.md` 文件，再返回 `{"chunks": ...}`，由 LangGraph 合并到 State 并交给后续节点。

这个实现已经处理了路径缺失、路径不存在、空文件和换行符差异，也通过代码块状态避免了一部分标题误判。当前需要注意的是，`kb_main` 版对标题前导空格的判断还没有同步学习版的修正；另外，围栏结束标记的判断比较严格，复杂 Markdown 语法下仍有改进空间。

# 10. 可优化点

## 10.1 【当前已经实现】

- 已校验 `md_path` 是否提供、路径是否存在以及文件内容是否为空字符串。
- 已在缺少 `file_title` 时使用 Markdown 文件名作为默认标题。
- 已统一不同操作系统产生的换行符。
- 已按一到六级 Markdown 标题组织章节。
- 已通过代码围栏状态避免把正常围栏代码块内的 `#` 误判成标题。
- 已区分短章节、表格章节和普通长章节。
- 已使用递归字符切分器，并配置 300 字目标长度和 30 字重叠。
- 已为未拆分章节设置 `part=0`，为长章节片段按顺序设置 `part=1、2、3……`。
- 已把章节标题和文件标题附加到切片数据中。
- 已把最终切片列表序列化到本地备份文件，并通过 State 返回 `chunks`。

## 10.2 【学习版与封装版的实际差异】

- `backup` 学习版把校验、章节识别、长文本切分和备份写入集中在一个 `process()` 中；`kb_main` 版拆成 `process_md_content()`、`get_section_list()` 和 `get_chunks_list()`。方法拆分本身没有改变核心业务目标。
- 学习版显式传入 `length_function=len`；封装版将这一行注释。当前切分器默认仍按字符串长度计算，因此这里不构成功能差异。
- `backup` 版已经修正标题前导空格问题：只规范化标题字段，不清除正文缩进，并根据标题字段剥离首行。
- `kb_main` 版尚未同步上述修正，带前导空格的标题可能被保存为“无标题”。这是当前两版中会实际影响切片结果的逻辑差异。

## 10.3 【未来可以优化】

- 将 `backup` 中已经验证的标题规范化逻辑同步到 `kb_main`，同时保留代码块、嵌套列表和 Markdown 强制换行所依赖的原始空格。
- 改进代码围栏判断：结束围栏应校验符号类型、最小长度和尾部内容，而不只是要求字符串与开始标记完全相等。
- 使用成熟的 Markdown 解析器处理标题和代码块，减少简化正则面对复杂 Markdown 时的误判。
- 使用 `is_file()` 明确校验输入是文件，并把纯空白文档也纳入空内容判断。
- 对 `<table` 进行不区分大小写的判断，或先把独立表格块提取为完整切片，避免一个表格导致整章无限制保留。
- 把 `chunk_size`、`chunk_overlap` 和分隔符列表提取到配置中，以便根据模型上下文长度和文档类型调整。
- 明确无标题长文本的输出策略，避免把程序占位值“无标题”误写成原文内容。
- 将备份文件扩展名改为 `.json`，或者真正生成 Markdown 格式，保持文件扩展名与内容一致。
- 对备份写入失败提供更明确的错误信息，并根据业务需要决定“备份失败”是否应中断切片结果返回。
